**编制日期**：2026-10-10　　**适用范围**：Vue 3 + Spring Boot + FastAPI + LangGraph + MySQL + ClickHouse 多租户 SaaS

> **文档效力**：本规范用于开发、代码审查、自动测试及发布门禁。标记“强制”的规则不得跳过；“建议”的配置须经过真实流量画像和压测冻结。本文的 P95、RPO/RTO 与 99.9% 均继承已有需求基线，是尚需验证的设计目标，不代表当前工程已经达到生产 SLA。不得为提升性能跳过租户隔离、权限、发布批次校验和数据正确性检查。

## 1. 目的、范围与规范等级

### 1.1 目的

针对多租户并发访问、看板聚合查询、异步同步与导出、AI 编排、支付和用量结算，提前建立可执行的限流、背压、熔断、舱壁隔离、降级、幂等、恢复和可观测性规范，防止单点故障扩散为跨模块或跨租户雪崩。确保“功能正确、故障可控、容量可测、问题可定位、服务可恢复”。

### 1.2 等级定义

- **MUST（强制）**：未满足时 PR 不得合并、相应功能不得发布；例外须经架构/安全审批并记录失效期及补救措施。
- **SHOULD（建议）**：默认实施；如需调整，必须提供容量、成本与风险说明及测试证据。
- **MAY（可选）**：按复杂度和商业套餐实施，不影响 P0 关键链路。
- **P0/P1/P2**：遵循需求规格的功能优先级，不等于故障告警等级；租户隔离、计算正确性、只读查询不可降级。

### 1.3 范围和依赖边界

- **Vue3**：页面容错、请求合并、取消、可见性控制、错误边界、SSE 恢复。
- **Spring Boot**：鉴权、租户资源治理、并发舱壁、查询调度、幂等、事务边界。
- **FastAPI / LangGraph**：AI 任务并发、模型调用限额、Graph checkpoint、工具重放治理。
- **MySQL / ClickHouse**：连接池、事务、查询计划、读写隔离、发布版本、数据对账。
- **Redis / RabbitMQ / Worker**：分布式限流、短期缓存、消息去重、任务续租与背压。
- **Kubernetes / SRE**：资源配额、弹性伸缩、监控、告警、灰度和灾备演练。

## 2. 可靠性目标、压测基线和容量预算

### 2.1 上游需求基线（非现状成绩）

| 维度 | 需求基线 | 计量说明 |
|---|---|---|
| 示例负载 | 100 租户、1,000 成员、100 并发活跃用户 | 不等于 100 RPS；需分别记录活跃用户数、请求速率和查询复杂度 |
| 示例数据量 | 单主要事实表 1,000 万行、日新增 100 万行 | 含修订、重放、跨日更新及历史维度 |
| 元数据 API | 服务端 P95 ≤ 500 ms | 区分缓存命中/未命中，公布样本量 |
| 聚合/缓存图表 | P95 ≤ 3 s | 基于批准的数据集/指标、规定缓存比例 |
| 看板首屏可操作 | P95 ≤ 5 s | 浏览器端指标，包含组件加载 |
| 支持的 AI 问题 | P95 ≤ 20 s，总时限 60 s | 不含等待用户澄清；标注供应商/模型/并发 |
| 交互查询 | 默认超时 30 s、返回上限 10,000 行 | 超时应终止数据库实际查询 |
| 单租户查询 | 默认最多 5 个运行、20 个排队 | 全局容量另配，不可无限排队 |
| 可用性 | 月可用性设计目标 99.9% | 合同明确入口、成功判定与维护窗口 |
| 恢复目标 | MySQL：RPO≤15 min、RTO≤4 h；已发布分析数据：RPO≤1 h、RTO≤8 h | 每季度至少一次真实恢复演练 |

### 2.2 资源预算（MUST）

1. 每类请求必须定义 **最大并发数、最大排队长度、排队等待时间、总截止时间、内存/扫描预算、结果大小上限**；所有阈值集中配置，按环境和套餐可调整。
2. 资源预算必须实行 **全局→租户→用户/工作空间→任务类型** 多层控制；任何一层被耗尽时主动拒绝或排队，而非无界阻塞。
3. 交互查询、后台同步、导出、AI 工具和定时报告使用不同任务队列/执行池，并按成本设置优先级和并发隔离。
4. 请求经网关到 Java、Java 到 Python/数据库时，必须传播 **deadline、trace_id、task_id、tenant_id（由服务端确认）**；下游超时不得超过剩余 deadline。
5. 不得通过关闭权限、减少数据完整性校验或返回过时未标注结果换取 P95。

### 2.3 新增建议阈值（需专项压测后冻结）

| 治理项目 | 初始建议 | 说明 |
|---|---|---|
| 交互接口排队超时 | 0.5–2 s | 超时返回限流/系统繁忙，不能持续占用连接 |
| 单租户 AI 活跃任务数 | 2–3 | 与套餐和模型供应商配额联动；非上游固定要求 |
| 非幂等外部调用自动重试 | 0 次 | 未实现幂等键前禁止自动重试 |
| 幂等且可恢复调用重试 | 最多 2 次，指数退避+抖动 | 必须保证重试仍在总体 deadline 内 |
| 高成本查询结果缓存 | 按权限/版本键，短时限并带失效通知 | TTL 不是安全控制机制 |
| 看板自动刷新 | 不短于 60 s | 隐藏标签页暂停，用户可手动刷新 |
| 单图表并发请求 | 合并同计划请求；对同一页面设置有界上限 | 由浏览器性能测试确定具体数值 |

## 3. 系统架构与故障隔离原则

### 3.1 多级防线（MUST）

请求入口顺序建议：**Ingress/WAF 限速 → Spring Security 身份与租户校验 → 套餐/租户配额 → 资源舱壁 → 有界队列 → 授权查询计划 → 数据库/模型执行 → 结果与权限复核 → 审计/用量**。每个环节具有明确失败出口。

### 3.2 故障域划分（MUST）

- **租户故障域**：租户 A 占满自身额度，不能挤占租户 B 的最小保障资源；超大租户升级使用独立资源池时仍执行逻辑权限。
- **任务类型故障域**：导出或全量同步占用 CPU/内存时，登录、元数据及已发布看板仍可用。
- **依赖故障域**：外部 LLM 超时只能影响 AI 能力；源数据库故障只能影响该数据源；ClickHouse 故障不能拖垮身份认证与订阅服务。
- **结果故障域**：单图表失败显示局部错误，不造成整个看板白屏；单个 Graph 节点失败进入可恢复状态，不重复扣费。

### 3.3 降级顺序（MUST）

资源紧张时依次限制：**非紧急后台同步/预计算 → 大文件导出 → 高成本 AI 深度分析 → 自动刷新频率**；尽可能保留登录、权限校验、租户管理、已发布且已授权的基础 BI 查询。必要时明确进入只读/繁忙模式。降级禁止放宽安全策略、允许未发布数据可见、隐藏业务错误或伪造分析结论。

## 4. Vue3 前端高并发与容错规范

### 4.1 请求与组件（MUST）

1. 所有请求经统一 `src/api/client.ts` 或等价封装：设置合理超时、取消、错误码映射、trace_id 展示及 401/403/409/429/503 的明确处理。
2. 页面路由懒加载；ECharts 按需加载；大表虚拟滚动及服务端分页；禁止拉取百万行明细在浏览器做全量统计。
3. 搜索和筛选输入使用防抖；看板内相同 QueryPlan/相同版本的请求必须合并。用户快速切换筛选时取消旧请求，并用请求序号避免乱序结果覆盖新结果。
4. 自动刷新不短于 60 秒；隐藏标签页暂停或降低频率；刷新前确认之前的同类请求是否仍在执行。
5. 每个图表具有 `loading / empty / partial / error / forbidden / rate_limited / stale` 等状态；错误边界保护整个面板，拒绝白屏。
6. 无权限数据不可通过前端过滤或隐藏列处理；服务端必须先裁剪字段和行范围。
7. 租户切换、退出登录、权限版本变化时主动取消在途请求、断开 SSE、清空有租户上下文的 Pinia/查询缓存。

### 4.2 AI 流式与用户体验（MUST）

- SSE 事件包含 `task_id / sequence / type / trace_id`。网络断开通过原任务 ID 和最后 sequence 重连，不应重新建立收费任务。
- 状态展示区分：排队、执行中、等待澄清、部分结果、已完成、失败、取消与超时；超时不显示为“成功”。
- 页面关闭或点击取消时向后端发送取消请求；最终状态以服务端 Worker 和数据库真实停止结果为准。
- AI 返回的图表配置只能经过 JSON Schema 验证，禁止执行模型产生的 JavaScript/HTML。

### 4.3 前端验收（MUST）

连续快速筛选、弱网断流、HTTP 429/503、单图表报错、权限撤销和租户切换均不得白屏、串租户、展示过期的越权缓存；首屏目标按 §2 测量。

## 5. Spring Boot 服务端并发规范

### 5.1 分层与事务（MUST）

- 保持 `Controller → Service 接口 → ServiceImpl → Manager → Mapper → Entity` 分层；Controller 只做协议、参数、调用与响应适配；Service 管理业务事务，Manager 封装受控查询或外部资源协调。
- `@Transactional` 仅包围必需的数据库写操作，不把网络请求、ClickHouse 查询、LLM 生成和文件传输置于长事务。
- 共享组件默认无会话可变字段；用户与租户上下文不能存放在单例对象的可变字段中。线程池/异步任务跨线程传递上下文采用显式不可变对象，且在任务结束时释放。
- 禁止未经评审的 `synchronized` 大锁、无限队列、默认无界线程池、阻塞式循环重试。每个线程池应有 `core/max/queue/rejection` 的配置与指标。

### 5.2 并发准入、限流和背压（MUST）

1. 入口按 IP/身份/租户/接口维度进行令牌桶或等价限流；全局限额与租户限额同时生效。
2. 请求处理前获取资源许可证（例如查询信号量），申请失败立即 429 或返回有限排队凭证；不允许排队占用 JDBC 连接。
3. 交互查询默认每租户 5 运行/20 排队；平台全局池和单用户子池必须有上限。调度采用租户级公平策略，禁止“先到先得”长期饿死小租户。
4. 429 响应包含稳定业务错误码、trace_id、合理 `Retry-After`（如已知）；前端不应指数级放大重试流量。
5. 线程池饱和、JDBC 池耗尽、队列过长时触发拒绝/降级，不能把连接超时扩散至整个 Java API。

### 5.3 超时、重试、熔断、舱壁（MUST）

- 调用链使用统一 deadline：**连接超时、读取超时、队列等待超时、整体业务超时** 分别配置；下游预算必须小于调用方剩余预算。
- 重试仅针对确定的暂时性错误和安全幂等操作，使用指数退避、随机抖动、上限和重试预算；禁止对 400/401/403/422 或不可恢复配置错误重试。
- 熔断以供应商/数据源/查询类型为维度，按窗口错误率与慢调用触发；半开状态限制探测流量。
- Bulkhead 按 AI、查询、导出、连接器分别配置线程、连接及并发许可；一个依赖异常不能占满全局 HTTP 线程。
- 所有资源获取均用 `try/finally` 或等价自动释放模式；取消、超时、中断场景同样释放连接和许可证。

### 5.4 幂等与并发正确性（MUST）

订单创建、同步触发、导出创建、AI 请求和支付回调均应具备业务唯一执行 ID 或 `Idempotency-Key`。同一键相同参数返回原结果，同键不同参数返回 409；唯一键和数据库 CAS 是权威防重手段。库存、配额、席位、计费等竞争更新使用原子 SQL、乐观锁或必要的行级锁，严禁“先读后写”无约束扣减。

## 6. FastAPI / LangGraph AI 并发治理

### 6.1 入口和执行模型（MUST）

- FastAPI 只接受 Java 发出的内网签名/短期委托任务；身份和租户均由 Java 重新确认，禁止信任模型内容中的 tenant_id。
- 异步端点不得调用会长时间阻塞事件循环的同步 I/O/CPU 密集代码；阻塞操作使用受控执行器或独立 Worker，并设置并发上限。
- 按租户、模型、供应商分别限制活跃 AI 任务、模型并发和 Token 预算，拒绝无限创建 Graph 实例或外部模型请求。
- Graph 节点有独立超时；需求建议整个 AI 请求最多 8 次工具调用、2 次计划/SQL 修正、60 秒总时限；重试不能重置总体 deadline。

### 6.2 Checkpoint 与恢复（MUST）

- 生产使用独立持久化 LangGraph Checkpointer；不得用 `InMemorySaver` 作为生产唯一状态。缓存 Redis 与 checkpoint 实例/资源预算分离，checkpoint 不使用淘汰敏感状态的策略。
- `thread_id` 绑定 `tenant_id、member_id、conversation_id`，由服务端生成；任务恢复前重新检查身份、权限版本、数据集/指标版本和配额。
- 工具调用有 `tool_execution_id` 幂等记录。Graph 节点重放不得再次发布数据、发送报告或重复扣用户请求次数。
- 取消时同步终止正在执行的 Java 查询、外部模型流及后续 Graph 节点；保留必要的失败/取消审计。

### 6.3 模型服务故障降级（MUST）

模型超时、限额或区域策略不满足时返回明确错误；受授权的传统指标查询与看板继续工作。模型故障切换只在租户批准的供应商/处理区域内进行，不能因“可用性”绕开数据外发策略。所有事实数值由 Java/ClickHouse 工具结果确认，模型无权补造数据。

### 6.4 计费安全（MUST）

业务请求计数使用 `reserve → commit/release` 原子状态机；一次用户 AI 任务只扣一次请求额度。模型重试可能产生实际 Token 成本，应单独累积和标记；账本与实际供应商成本分开。并发 100 次相同/不同幂等键请求后配额不得为负、不得重复扣款。

## 7. MySQL 性能与事务稳定性

### 7.1 SQL 与表设计（MUST）

1. 列表必须分页并限制最大 page size；禁止大 OFFSET 的深翻页作为批处理方案，优先稳定排序的游标/键集分页。
2. 关键查询按 `tenant_id + 业务过滤字段 + 排序字段` 验证复合索引，使用实际 `EXPLAIN ANALYZE` 或执行计划证明；不能盲目对每列加索引。
3. 禁止 N+1 查询、无条件全表扫描、大事务和不受控批量更新；迁移涉及大量数据时分批、可恢复、可暂停。
4. 事务内不调用 LLM、外部 Webhook、ClickHouse、对象存储，避免锁持有时间随外部延迟放大。
5. 读写分离必须标注复制延迟以及“读己之写”一致性要求；租户授权/发布指针/计费等强一致读取应读权威来源。
6. MySQL 连接池按实例总数规划：`实例数 × 每实例最大连接数` 不得超过数据库可用连接预算，并保留管理/复制余量。

### 7.2 一致性（MUST）

- 租户资源使用 `(tenant_id, resource_id)` 复合约束防止跨租户引用；租户注销标记优先于缓存恢复。
- 任务状态使用乐观版本或条件更新；不能把 Worker 日志“成功”视为事务已提交。
- 业务表与 Outbox 事件同一 MySQL 本地事务提交；RabbitMQ 消费端使用 Inbox/幂等键去重。
- 采用 Flyway 增量迁移；先加字段再迁移再切流最后清理旧字段，回滚不得丢失账本和已发布版本。

## 8. ClickHouse 查询与分析数据稳定性

### 8.1 受控查询（MUST）

- 浏览器和 Python 不直接连接 ClickHouse；只允许 Java 查询编译器从已发布语义模型生成白名单 SQL。
- 查询必须经 tenant/workspace、行列权限、数据集版本和发布指针验证；禁止仅在 SQL 尾部拼租户条件、禁止任意模型自由 SQL。
- 为查询类型配置 `max_execution_time`、内存与扫描预算、结果行数、只读用户 profile；不同租户/队列使用公平并发限制。
- 查询绑定服务器生成的 `query_id`；客户端取消或请求超时后必须实际终止数据库侧查询，不只是停止 HTTP 等待。
- 高基数 GROUP BY、无边界 JOIN、系统表、外部函数、文件读写等默认拒绝，除非进入专门审批的白名单。

### 8.2 版本与正确性（MUST）

- 同步数据先进入未发布批次；通过质量验证、金额/行数对账后以 MySQL CAS 更新 `generation_id + committed_publish_seq`。
- 查询只能看到已发布代和序号；写入成功但 MySQL 未推进发布指针时旧版本仍然可读。
- 修订、重放采用 `(tenant_id, source_id, business_key, event_version)` 或等价去重逻辑；不能依赖 ClickHouse 后台合并时机保证即时准确。
- 时间区间、时区、退款、去重、维度基数和币种必须采用已发布指标版本；禁止因加速而略过质量门禁。

### 8.3 容量治理（SHOULD）

按查询模式设计分区、排序键、预聚合和冷热分层；避免按每租户盲目建立大量物理分区。新建物化视图先评估写入放大、后台合并负荷与历史回填成本。重要性能变化提供基线 SQL、Explain、扫描量、CPU/内存及 P95/P99 对比。

## 9. Redis、缓存和分布式协调

### 9.1 缓存安全（MUST）

- 缓存键至少包含：`tenant_id + 授权主体/等价权限指纹 + policy_version + dataset_version + metric_version + data_generation/publish_seq + 参数 + 时区`。
- 权限撤销后无新结果可见；需求验收还要求缓存失效在 60 秒内完成。敏感数据交付前必须实时授权复核，不能只靠短 TTL。
- 防止缓存穿透、击穿与雪崩：非敏感空结果短期缓存、热点请求 single-flight 合并、TTL 抖动、后台重建有界并发。
- 不缓存含禁止字段的原始结果；租户切换时清理所有客户端租户作用域缓存。

### 9.2 Redis 依赖降级（MUST）

Redis 缓存异常时允许在有界资源和授权前提下回源；若无法可靠确认授权、额度或任务唯一性，则应拒绝相关高风险操作，不能 fail-open。限流 Redis 故障时启用本机保守限流并报警，跨实例全局配额仍须由权威存储保证。Graph checkpoint 独立持久化与备份。

### 9.3 分布式锁（MUST）

Redis 锁只减少争用，不单独承担发布唯一性；所有业务关键状态须使用 MySQL CAS、租约和递增 fencing token，防止过期持锁者继续写入。

## 10. RabbitMQ、同步 Worker 和导出任务

### 10.1 任务队列（MUST）

- RabbitMQ 至少一次投递的语义下，生产者使用 Outbox，消费者按事件 ID/批次 ID 去重；只有持久化业务结果后才 ACK。
- 设置有限的 prefetch、消费者并发、队列容量与待处理预算；超限进入背压/拒绝，禁止继续无限生产消息。
- 失败分为暂时性/永久性：可恢复同步错误遵循需求默认最多 3 次指数退避重试，永久错误进入隔离队列/死信，人工修复后显式重投。
- 连接器 Worker 按数据源/租户限制连接和扫描速率，避免把客户源库打满；导出使用独立 CPU/内存与文件流式处理池。
- 任务状态包含 `QUEUED / RUNNING / PARTIAL / SUCCEEDED / FAILED / CANCEL_REQUESTED / CANCELLED / TIMEOUT` 或等价映射，状态转移使用数据库 CAS；只有进程确认终止才可标记已取消。

### 10.2 同步一致性与恢复（MUST）

首次全量写隔离 generation，校验后发布；增量采用稳定主键+复合水位，先提交数据并对账，再推进水位。进程宕机、消息重放、迟到更新和数据源短断重连后必须做到不漏数、不重复累计，失败时沿用上一已发布版本并标注新鲜度。

### 10.3 导出（MUST）

导出任务采用异步、流式分页和独立资源池；默认最多 100 万行。任务执行与交付前均验证权限；文件保存在租户隔离对象存储，经应用层重新鉴权领取，下载权限失效不能单靠已签发的静态 URL 处理。

## 11. 多租户安全与公平调度

### 11.1 隔离矩阵（MUST）

| 访问面 | 强制校验 | 高并发风险与应对 |
|---|---|---|
| REST/SSE | 身份、tenant、member、permission_version | 断线重连不复用旧授权结果 |
| QueryPlan/SQL | tenant、workspace、字段、行级策略、发布版本 | 租户不能借缓存/子查询逃逸 |
| Worker/导出 | 任务持有人、接收者、租户、执行时权限 | 队列延迟导致权限过期时拒绝交付 |
| Redis/Graph state | tenant namespace、会话归属、权限版本 | 线程 ID 不可预测且不授予访问权 |
| 对象存储 | tenant 路径、文件身份、即时下载鉴权 | 失效令牌不能继续下载旧文件 |
| 监控/日志 | trace 关联、数据最小化 | 标签不含敏感 ID 明细，禁止记录密钥 |

### 11.2 公平性验收（MUST）

至少使用 20 个租户同时执行查询，其中一个租户主动制造高成本或超额流量。要求其他租户仍可获取保留的资源预算，不能因单一租户造成平台级连接池耗尽或 AI/看板全面不可用。报告按租户分组的吞吐、排队、429、P95/P99 和失败率；不能只报全局平均值。

## 12. 安全防护与稳定性协同

必须防御慢请求、恶意大分页、异常筛选、递归查询、提示词注入、数据库连接探测和资源型拒绝服务。仅允许已批准 SQL 函数/表/字段，采用 AST/DSL 编译；输入参数采用绑定，不接受任意拼接。外部模型数据发送前应用敏感字段与租户数据处理策略；任何熔断或故障回退不得绕过鉴权、模型外发策略或审计。

## 13. 可观测性、告警与运行手册

### 13.1 必需指标（MUST）

| 层级 | 核心指标 | 告警关注点 |
|---|---|---|
| 入口/API | RPS、P50/P95/P99、4xx/5xx、429、in-flight | 延迟上升、错误率、限流与吞吐突变 |
| Java | CPU、堆/GC、线程、JDBC 池使用/等待、队列积压 | 连接池耗尽、线程池拒绝、内存持续增长 |
| MySQL | 活跃连接、慢查询、锁等待、复制延迟、事务回滚 | 锁争用、长事务、复制落后 |
| ClickHouse | query_id、扫描量、内存峰值、查询超时、合并队列 | 大查询、OOM、parts 激增 |
| Worker/MQ | ready/unacked、重试率、DLQ、消费延迟、租约过期 | 背压失效、重复消费、死信堆积 |
| AI | 首 Token/结果延迟、Graph 节点耗时、工具调用次数、Token/成本、checkpoint 错误 | 模型故障、成本异常、恢复失败 |
| 数据质量 | 同步水位延迟、行数对账、批次发布时延 | 错批、漏数、未发布数据可见 |

### 13.2 Trace 与日志（MUST）

跨 Java、Python、Worker、MySQL 查询和 ClickHouse `query_id` 贯穿 `trace_id`；日志使用结构化 JSON、错误分类、租户的不可逆聚合维度。不得输出明文凭据、令牌、业务明细、完整模型敏感提示词。监控维度控制标签基数，不把每个用户、任务 ID 作为 Prometheus 指标标签。

### 13.3 告警执行（MUST）

每个 P0/P1 业务告警绑定负责人、触发条件、影响范围、诊断入口、隔离/回滚开关、恢复步骤和复盘模板。告警阈值通过压测确定并形成配置版本；不能仅凭 CPU 80% 单指标断定服务不可用。

## 14. Kubernetes/容器高可用与发布

- 生产 Java API、FastAPI 至少跨故障域部署多个副本；健康检查区分 startup、readiness、liveness，避免依赖短暂波动诱发重启风暴。
- 配置 requests/limits、Pod 优雅退出、连接排空、任务租约归还、滚动发布策略和 PDB；后台 Worker 与在线查询部署分池。
- HPA/队列伸缩需结合 CPU 与真实排队延迟/积压，设置冷却窗口和上下限，不能仅靠平均 CPU 证明扩容有效。
- 发布遵循 Expand→Migrate→Switch→Contract 数据库迁移顺序，实行灰度+自动回滚；兼容性与数据账本优先于代码回滚速度。
- 基础设施不得暴露内部 FastAPI、ClickHouse、Redis、RabbitMQ 管理端口于公网；密钥经 Secrets/KMS 注入且轮换可验证。

## 15. 容灾、备份与故障恢复规范

### 15.1 恢复目标（继承需求基线）

MySQL RPO ≤15 分钟、RTO ≤4 小时；ClickHouse 已发布分析数据 RPO ≤1 小时、RTO ≤8 小时。恢复工作必须包含 MySQL 元数据、数据发布指针、ClickHouse 有效版本、对象文件、密钥引用、消息任务水位、AI checkpoint 与租户删除标记。季度至少进行一次实际恢复演练。

### 15.2 必测故障注入（MUST）

1. Java 或 Python 单个 Pod 被杀死，其他副本继续服务，任务不会重复收费。
2. Redis Cache 不可用；授权操作要么安全回源要么拒绝，不泄漏租户数据。
3. Graph checkpoint 不可用：运行任务可解释地失败或安全暂停，恢复后鉴权仍有效。
4. ClickHouse 正在写批次时故障：不发布半成品，不返回“成功”数据。
5. MySQL 已提交任务但消息未投递：Outbox 重投，不丢任务、不重复扣款。
6. RabbitMQ 重复投递、Worker 过期租约：fencing 和幂等不允许双发布。
7. 外部模型超时和大量 429：AI 限流/熔断，传统看板保持服务。
8. 20 个租户混合读/同步/AI/导出，一租户压满自身配额，其他租户不被整体拖垮。
9. 停用成员或撤销权限发生在任务执行中：执行前/交付前复核，旧缓存和下载链接拒绝。
10. 从备份恢复后已注销租户不得复活，历史版本与数据对账仍可追溯。

## 16. 性能测试、容量评估与验收门槛

### 16.1 测试分层

| 测试级别 | 建议工具 | 核心检查 |
|---|---|---|
| 单元/组件 | JUnit 5、pytest、Vitest | 限流算法、幂等 CAS、前端错误边界、Graph 节点分支 |
| 接口与集成 | Testcontainers、pytest、Playwright | 真实 MySQL/ClickHouse、SSE、MQ、权限和取消 |
| 基线性能 | k6 / JMeter | API P50/P95/P99、吞吐、资源与正确性 |
| 混合负载 | k6 + Worker 回放脚本 | 看板/AI/同步/导出并行执行，无级联故障 |
| 故障注入 | Kubernetes 故障脚本/网络故障 | 单依赖失效、恢复时数据与账本一致 |
| 长稳/容量 | 持续负载、峰值与突刺 | GC、内存泄漏、连接泄漏、队列增长、拐点容量 |

### 16.2 必测流量方案（建议，压测前确认）

- **基线**：100 并发活跃用户、100 租户、1,000 万行主要事实表；同时启动后台增量同步及少量导出，记录缓存命中率。
- **突刺**：在基线基础上快速提升到 2–3 倍请求压力，验证有界拒绝、429/503、恢复时间；不得出现线程/内存无界增长。
- **公平性**：20 租户同时分析，其中 1 租户持续高成本请求；其他租户基本功能仍可执行。
- **长稳**：建议先 2–4 小时，付费发布前按关键链路延长至 12–24 小时；检查内存/连接和队列是否持续增长。
- **故障期间负载**：在混合压测中重启 Python、阻断模型供应商、降速 ClickHouse、堆积 MQ，验证局部降级。

### 16.3 明确的发布阻断项（MUST）

- 任一跨租户泄漏、越权访问或权限撤销后新结果泄漏；**一票否决**。
- 指标结果错误、同步重放后重复累计、已发布批次不可对账；**一票否决**。
- 账本负数、重复扣款、同幂等键多次任务副作用；**一票否决**。
- 生产关键资源无上限（线程、队列、连接、任务、结果）；**一票否决**。
- 取消后数据库查询仍长期运行、超时链未生效、故障回退造成 fail-open；**阻断发布**。
- 需求中对应的性能 P95 / RPO / RTO 未满足且无签署的容量调整或豁免；不得宣称达标。
- CI 中阻断级测试失败、无追踪号、无关键运行告警和回滚手册；阻断正式发布。

### 16.4 测试报告必填字段

环境拓扑、组件版本、CPU/内存配额、租户数、并发用户、RPS、数据规模、冷热缓存比例、AI 供应商和模型、请求样本量、P50/P95/P99、吞吐与错误率、限流/熔断数量、队列深度、资源曲线、正确性对账、租户公平性、故障影响、恢复时间、原始日志/trace、复现命令、结论与负责人。
